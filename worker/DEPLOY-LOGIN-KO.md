# 한국 시간 자정까지 로그인 유지 — 배포 안내

이 문서는 배포 절차입니다. 실제 운영 배포를 완료했다는 기록은 아닙니다.

## 적용 순서

`운영 소스 백업·비교 → SESSION_SECRET 설정 → PR 브랜치의 Worker 배포 → PR 머지 및 프론트엔드 배포 → 검증 → DEPLOYMENTS.md 기록`

main 머지로 프론트엔드가 자동 배포되는 경우, **PR을 머지하기 전에 Worker부터 배포**합니다. 새 프론트엔드는 새 Worker와 SESSION_SECRET이 필요합니다. 새 Worker는 기존 프론트엔드의 Google 토큰도 계속 지원합니다.

## 1. 운영 소스 백업 및 배포 방식 확인

1. Cloudflare 대시보드 → Workers & Pages → `overtime-api` Worker를 엽니다. 기존 API 주소는 `https://overtime-api.ruleein.workers.dev`입니다. 실제 운영 Worker가 맞는지 확인합니다.
2. 현재 배포 버전 ID, 배포 시각, Worker 소스 전체를 안전한 위치에 기록·백업합니다. 설정값 중 비밀값은 문서·PR·스크린샷에 포함하지 않습니다.
3. 운영 소스를 PR의 기준 커밋과 비교합니다. 운영에서만 수정한 코드가 있다면 먼저 저장소와 동기화하여, 이번 파일 전체 교체로 운영 수정이 사라지지 않도록 합니다. 현재 저장소의 운영 배포 기준은 미확인 상태입니다.
4. GitHub 저장소 Settings → Pages에서 사용 중인 프론트엔드 배포 방식을 확인합니다. Deploy from a branch이면 브랜치·폴더를, GitHub Actions이면 실제 workflow를 확인합니다. Cloudflare Pages 등 다른 호스팅을 사용하면 해당 프로젝트의 연결 브랜치와 배포 경로를 확인합니다. 이 저장소만으로 실제 프론트엔드 호스팅 방식은 확정할 수 없습니다.
5. 기존 `index.html` 버전과 프론트엔드 배포 ID도 복구용으로 기록합니다.

## 2. SESSION_SECRET 생성 및 설정

개인 PC 터미널에서 다음 명령으로 충분히 긴 난수를 생성합니다.

```sh
openssl rand -hex 32
```

이 명령은 임의의 32바이트를 64자리 문자열로 출력합니다. 결과를 비밀번호처럼 관리하고, 채팅·PR·저장소에 붙여 넣지 않습니다. 아래 변수 이름만 고정이며 실제 값은 직접 생성한 난수입니다.

1. Cloudflare → 해당 Worker → Settings → Variables and Secrets(또는 Variables) → Add.
2. Type: **Secret**을 선택합니다.
3. Variable name: `SESSION_SECRET`.
4. Value: 방금 생성한 난수를 붙여 넣습니다. 줄바꿈이나 따옴표를 추가하지 않습니다.
5. Save/Deploy 등 대시보드의 저장 절차를 완료하고 **운영 배포에서 사용하는 설정**인지 확인합니다. 프리뷰 설정만 추가하면 운영에 적용되지 않습니다.

설정을 저장하면서 기존 Worker 버전이 다시 배포되는 UI일 수 있습니다. 이후 3단계에서 새 소스를 배포합니다.

- `GOOGLE_CLIENT_ID`, `GITHUB_TOKEN`, `GITHUB_OWNER`, `GITHUB_REPO`, `GITHUB_BRANCH`, `ALLOWED_ORIGIN`, `ADMIN_EMAILS`는 기존 값을 유지합니다.
- SESSION_SECRET을 GOOGLE_CLIENT_ID와 혼동하지 않습니다. Google 토큰 만료 검사를 끄지 않습니다.
- SESSION_SECRET은 매번 배포할 때 새로 만들지 않습니다. 변경하면 기존 앱 세션이 모두 무효화됩니다.
- 별도 KV/D1 세션 저장소, Google OAuth 재설정, 사용자 데이터 마이그레이션은 필요하지 않습니다.

## 3. Worker 먼저 배포

1. GitHub PR의 Files changed에서 `worker/worker.js`를 열고 **PR 브랜치의 파일 전체 내용**을 복사합니다. diff의 추가된 줄만 복사하지 않습니다. 머지 전이라 main에는 아직 새 코드가 없습니다.
2. 로컬에서 확인한다면 해당 PR 브랜치를 체크아웃하고 아래 명령을 실행합니다.

```sh
node --check worker/worker.js
node --test tests/*.test.mjs worker/*.test.js
```

3. Cloudflare Worker의 Edit code에서 기존 실행 파일(예: worker.js 또는 index.js)의 내용을 복사한 `worker/worker.js` 전체 내용으로 교체합니다. 파일명은 Cloudflare 프로젝트의 기존 진입 파일을 유지합니다.
4. Deploy를 누르고 배포된 버전 ID와 소스 커밋을 기록합니다. SESSION_SECRET이 해당 배포에 연결되었는지도 확인합니다.
5. 기존 화면으로 Google 로그인이 되는지 확인합니다. 기존 Google 토큰 요청은 계속 지원됩니다.

Cloudflare Workers Builds가 GitHub에 연결되어 자동 배포하는 환경이라면 수동 편집으로 이중 배포하지 말고, 실제 빌드 설정에서 위 순서가 지켜지도록 해당 소스 버전을 먼저 배포합니다. 저장소에는 wrangler 설정이나 Worker 자동 배포 workflow가 없어 기존 배포 설정 확인이 필요합니다.

## 4. PR 머지 및 프론트엔드 배포

1. Worker 배포가 완료된 다음 PR을 main에 머지합니다.
2. GitHub Pages가 main을 자동 배포한다면 Actions/Deployments에서 해당 머지 커밋의 배포 성공을 확인합니다. `/ (root)`를 사용하는 기존 설정이라면 index.html과 assets가 함께 제공됩니다. 사용 중인 배포 폴더는 임의로 바꾸지 않습니다.
3. Cloudflare Pages 등 다른 호스팅을 사용한다면 해당 프로젝트에서 동일 커밋의 배포 성공을 확인합니다. 수동 배포라면 기존 방식으로 새 index.html을 반영하고 assets 경로는 유지합니다.
4. 실제 서비스 주소를 새로고침하여 로그인 화면에 “Google 계정으로 로그인 후 이용할 수 있습니다.” 안내만 표시되는지 확인합니다. 오래된 화면이 남으면 먼저 강력 새로고침을 시도합니다. 사이트 데이터를 삭제하면 저장된 로그인도 삭제됩니다.
5. API 주소와 서비스 주소는 기존 값을 유지합니다. 도메인 변경은 이번 배포 범위가 아닙니다.

## 5. Safari와 Chromium에서 확인

일반 브라우징 모드에서 승인된 협력업체 계정과 현대건설 계정으로 각각 확인합니다. 실제 작업계획서를 임의로 수정·삭제하는 검증은 피하고, 필요한 쓰기 검증에는 합의된 테스트 문서를 사용합니다.

- Google 로그인 후 기존 목록과 상세 조회가 정상인지 확인합니다.
- 새로고침, 탭 닫기·재열기, 브라우저 종료·재실행 뒤 같은 브라우저/프로필/서비스 주소에서 로그인 복원 여부를 확인합니다.
- 휴대폰 잠금과 다른 앱 전환 후 돌아와도 자정 전에는 계속 이용 가능한지 확인합니다.
- Google 토큰의 일반적인 유효 시간인 1시간 이상이 지나도 자정 전에는 조회가 가능한지 확인합니다.
- 네트워크를 잠시 끊었다가 다시 연결하고 재시도합니다. 로그인 정보가 지워지지 않아야 합니다.
- 실제 한국 시간 자정(UTC 15:00)에 열린 화면이 로그인 화면으로 바뀌는지 확인합니다. 잠든 기기는 화면 복귀 시 처리됩니다. 자정 이후 서버 요청은 만료로 거부되어야 합니다. 운영 검증을 위해 PC 시계나 서버 만료 검사를 임의로 바꾸지 않습니다.
- 자정 이후 자동으로 Google 재로그인되지 않고 버튼을 눌러 다시 로그인하는지 확인합니다.
- 로그아웃하면 같은 출처의 다른 열린 탭도 로그아웃되는지 확인합니다.
- 기존 가입 대기·반려·이용정지 계정은 보호 API를 사용할 수 없어야 합니다.

개발자 도구 Network에서 최초 `/api/auth` 응답에는 `sessionToken`, `sessionExpiresAt`이 있고, 새로고침 후 복원 응답에는 새 세션이 발급되지 않는지 확인할 수 있습니다. 토큰은 비밀번호처럼 취급하며 캡처·공유하지 않습니다. 검증용 기기의 시간은 자동 설정을 권장합니다.

## 6. 장애 확인 및 복구

| 증상 | 확인·조치 |
| --- | --- |
| “로그인 유지 설정이 준비되지 않았습니다.” / SESSION_NOT_CONFIGURED | 실제 운영 Worker의 SESSION_SECRET 이름·Secret 타입·길이·적용 배포를 확인합니다. |
| “최신 서버 배포와 설정을 확인해주세요.” | 새 프론트엔드보다 Worker가 먼저 배포되었는지, 실제 API 주소가 해당 Worker인지 확인합니다. |
| 로그인 확인 실패 / 다시 시도 | 먼저 네트워크와 Worker 로그를 확인합니다. 5xx는 저장된 세션을 삭제하지 않으므로 복구 후 다시 시도합니다. |
| 배포 직후 기존 사용자가 다시 로그인해야 함 | 만료된 예전 Google 토큰은 새 세션으로 바꿀 수 없습니다. 최초 한 번의 재로그인이 필요할 수 있습니다. |
| 자정 전에도 모든 세션이 풀림 | SESSION_SECRET 변경 여부와 기기 시간 설정을 확인합니다. |

복구 순서는 **프론트엔드를 기존 버전으로 먼저 복구 → 필요시 Worker도 기존 버전으로 복구**입니다. 새 화면을 남긴 채 Worker만 되돌리면 로그인 호환성이 깨집니다. GitHub 자동 배포 환경에서는 이번 PR 변경을 되돌리는 별도 revert 커밋을 배포합니다. 공유 main을 강제 초기화하지 않습니다. Worker는 Cloudflare의 이전 배포 버전으로 복구하되 설정 적용 여부도 확인합니다.

복구를 위해 users.json, 작업계획서, 서명 데이터를 삭제하거나 되돌릴 필요는 없습니다.

## 7. 배포 기록

실제 배포와 확인이 끝나면 저장소 루트의 `DEPLOYMENTS.md`에 UTC 배포 시각, 소스 커밋, Cloudflare 버전/배포 ID, 배포자, 프론트엔드 배포 정보, 검증 결과를 기록합니다. 실제 Safari와 자정 검증을 아직 하지 못했다면 완료로 기록하지 말고 미확인 항목을 명시합니다.

## 세션 방식의 범위

앱 세션은 기존 구조처럼 브라우저 localStorage의 Bearer 토큰으로 보관합니다. 타사 쿠키나 Google 자동 로그인에는 의존하지 않습니다. 같은 브라우저·프로필·출처에서 유지되며, 시크릿 모드 종료나 사이트 데이터 삭제 후에는 재로그인이 필요합니다. HttpOnly 쿠키 방식은 이번 변경에 포함되지 않습니다.

로그아웃은 해당 브라우저 저장소와 열린 탭에서 세션을 지웁니다. 이 방식은 서버에 개별 세션 목록을 저장하지 않아 이미 복사된 토큰을 로그아웃만으로 서버에서 폐기하지는 못하며, 토큰은 자정 만료 또는 계정 이용정지로 차단됩니다. 기존 계정 상태·권한은 보호 요청마다 서버에서 확인합니다.
